1. Ringkasan Eksekutif

Backend GARAP API adalah layanan REST JSON yang melayani tiga jenis klien sekaligus: aplikasi web React (SPA), aplikasi mobile Flutter, dan perangkat ESP32 di lapangan. Backend ini merupakan hasil portingan dari aplikasi Laravel lama ke Node.js/Express dengan kontrak API yang dipertahankan 1:1 agar frontend lama tetap kompatibel.

Prinsip desain yang dipegang sejak gelombang refactor:

  • JSON-only — tidak pernah mengirim HTML; navigasi browser dibalas 204 kosong (by design).
  • Validasi SEBELUM SQL — input tak sah ditolak 422 terstruktur, tidak pernah sampai ke PostgreSQL (menutup seluruh kelas error 500 yang ditemukan pengujian hitam).
  • Kontrak byte-stabil — pesan 401/403/404/422 dikunci dan dijaga lewat suite integrasi agar klien tidak pernah terkejut.
  • 404 seragam anti-enumeration — id tidak valid dan id tidak ada menjawab identik.
  • Guard per-role — admin, petani, dan akun demo memiliki pintu masuk yang berbeda (demoGuard: demo hanya boleh POST ke route whitelist).
  • Net-zero pengujian — setiap tes tulis wajib mengembalikan keadaan database persis seperti semula.

5. Pipeline Request & Middleware

  1. express.json / urlencoded — parsing body; JSON rusak → 400 'Format JSON tidak valid.'; body > limit → 413.
  2. Middleware keamanan — X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy, Cache-Control: no-store, X-RateLimit; x-powered-by dimatikan.
  3. Perutean — mount per modul di index.js; rute tak dikenal → 404 JSON 'The route … could not be found.'.
  4. Guard otorisasi — requireAuth (Bearer ketat 'Bearer ') → requireRole → demoGuard (metode-aware: demo hanya POST whitelist) atau requireApiKey utk ESP32.
  5. Validasi — validateBody (Zod, skema lazy per tabel + cache panjang kolom), idValid/idOk (404 seragam), tanggalErrors() utk query date.
  6. Handler — kueri parameterisasi $n, pola RETURNING *, respons kontrak (200/201 {status,message,data} atau objek baris).
  7. Error-handler global — penerjemah akhir: entity.parse.failed → 400 JSON; status 400 klien → 'Permintaan tidak valid.'; SQLSTATE 23502/23514/23505 → 422 per-field; sisanya 500 generik 'Terjadi kesalahan pada server.' + stack hanya ke log.

Catatan: permintaan dengan header Sec-Fetch-Mode: navigate (dibuka dari address bar) dibalas 204 kosong — bukan error; lihat Bab 8.

7. Validasi Data & Kontrak Error

Validasi dibangun dari dua sumber: spesifikasi eksplisit TABLE_SPECS (per tabel, per kolom) dan inferensi longgar untuk kolom tanpa spesifikasi (tgl_*/tanggal → date, id_/jumlah_/waktu_* → integer, sisanya string 1..500). Batas panjang teks efektif = MIN(batas spec, panjang kolom aktual dari information_schema) sehingga tidak ada teks yang lolos lalu dibuang PostgreSQL.

KondisiResponsContoh pesan
Body/field tidak sah422{"message":"Data tidak valid.","errors":{"field":["pesan per-field"]}}
Rentang angka melewati batas kolom422"Kolom nilai harus antara 0 dan 99999999.9999."
Tanggal query rusak (?dari=bukan-tanggal)422"Filter dari harus berupa tanggal (YYYY-MM-DD / ISO-8601)."
Byte NUL pada input422"Kolom meja tidak boleh mengandung karakter terlarang."
FK tidak terdaftar422"id_meja tidak terdaftar."
Pelanggaran unik (SQLSTATE 23505)422"Email sudah dipakai." / "Username sudah dipakai."

Id tidak valid atau tidak ada404 identik{"message":"Data tidak ditemukan.","errors":{}}
Tanpa token / token rusak401"Tidak terautentikasi."

Urutan penjagaan pada rute tulis: validasi id (404) → baca baris lama (404) → validasi body (422) → cek FK/rentang (422) → query tulis. Urutan ini yang menjamin jawaban 404 tidak pernah bergantung pada isi body.

11. Keamanan

  • Parameterisasi penuh ($1…) di seluruh kueri — terbukti lewat 40 probe injeksi (OR 1=1, UNION, ;DROP, %00) dengan tabel utuh.
  • JWT rusak (secret salah, alg none, expired, dimanipulasi) semuanya 401 — 7 variant teruji; secret dibuat lokal utk tes, tidak pernah dibocorkan.
  • Mass-assignment dicegah whitelist kolom per route — field berlebih (role, id, created_at) diabaikan dan terbukti tidak tersimpan.
  • 404 seragam anti-enumeration + pesan error generik tanpa stack/SQL ke klien.
  • Header keamanan lengkap (nosniff, DENY, no-referrer, no-store, rate-limit) pada 6 kelas respons.
  • BFLA tertutup: petani ditolak rute pengelola, demo ditolak seluruh tulis di luar whitelist.
  • Rate limit login 10/menit/IP dengan spoof X-Forwarded-For tertangani pola deploy nginx + bind localhost.

Backlog keamanan terbuka (sengaja dicatat jujur): S2 TLS/HSTS di nginx, S3 helmet/CSP, S4 scope baca akun demo, S6 pagination semua list, S9 rate-limit in-memory, S10 fallback secret lemah di kode (aktif hanya bila .env kosong), risiko api_key pada body ESP32.

12. Kinerja & Caching

  • cache.js: latest-sensor 2 dtk, thresholds 60 dtk — polling ESP32/SPA tidak membebani database.
  • Partisi sensor_readings per bulan + indeks sargable /laporan (skrip index_laporan.sql DRAFT).
  • Keep-alive tuning: keepAliveTimeout 65 dtk, headersTimeout 70 dtk, requestTimeout 30 dtk — menahan churn koneksi seribu pengguna.
  • Uji beban historis: 141 ribu request/20 detik pada versi sebelumnya.

13. Pengujian

  • 106 tes (node --test + supertest): 4 unit + 102 integrasi — cakupan auth, RBAC/403 demo, 404 byte-identik, 422 per-field, mass-assignment, ESP32, query aneh, 5 header wajib, laporan, water control.
  • Aturan net-zero: setiap tes tulis membersihkan barisnya dan memverifikasi hitungan baseline (mejas=5, users=3, monitorings=12, alert_logs=51).
  • Hemat login: helper _server.js membatasi maksimal 3 POST /login per server test.
  • Pemeriksaan tambahan: node --check 22 file, npm run build + oxlint (frontend), smoke-test.sh 20 pemeriksaan.
  • Disiplin gerbang: setiap perubahan kode dinilai verifier independen sebelum commit (stempel [verified:deleg_…] pada subjek commit).

Lampiran A — Contoh Permintaan

Login → token:

curl -X POST http://127.0.0.1:8000/login -H 'Content-Type: application/json' -d '{"username":"admin","password":"<dari .env>"}'

Pakai token (daftar meja, 13 kolom):

curl http://127.0.0.1:8000/meja -H "Authorization: Bearer <token>"

Endpoint ESP32:

curl http://127.0.0.1:8000/api/get-thresholds -H "X-API-KEY: <ESP32_API_KEY>"

Contoh tolak validasi (422):

curl 'http://127.0.0.1:8000/laporan?dari=bukan-tanggal' -H "Authorization: Bearer <token>"

→ 422 {"message":"Data tidak valid.","errors":{"dari":["Filter dari harus berupa tanggal (YYYY-MM-DD / ISO-8601)."]}}
